# AWS AgentCore / Bedrock Research — Memory, Models, Code Interpreter, Evaluations

**Scope:** Research only — no implementation, provisioning, credentials, or deployment. Every factual claim cites a specific AWS doc page fetched 2026-10-23. Where a claim isn't established by the pages reviewed, it's flagged **UNVERIFIED** rather than assumed. No GA/region/model/latency SLA is asserted unless the source says so. **The verdicts in Section 5 are research-level candidate recommendations for further evaluation, not an approved architecture decision or implementation commitment** — nothing here authorizes building, deploying, or wiring any of these services into the project.

**Project facts (given, not independently re-verified against AWS):** five deterministic Python seat runtimes share an immutable profile and a **per-invocation normalized snapshot** (not a guaranteed byte-identical, globally-synchronized "one canonical per-tick" state — the five seats' snapshots arrive asynchronously and are not guaranteed identical across seats on a given tick); each player computes presser/cover/marking independently, no shared state/network/model call on the hot path (`agent/tactics.py:100-139`); target is AgentCore Runtime, CodeZip, Python 3.12, `us-east-1`; formation `1-1-2` fixed pre-match; desired decision latency ~1s, with a non-authoritative 5s fitness ceiling and project-measured cold network checks of **up to ~4.511s** (a single worst-case figure, not a range) vs ~0.5ms deterministic planning; an offline SQLite trainer and an **optional** LangChain/Bedrock advisor (`agent/advisor/core.py`; `agent/advisor/__main__.py:18-24` via `langchain_aws.ChatBedrockConverse`) produce bounded, Pydantic-validated (`extra=forbid`) JSON proposals, never auto-deployed (`__main__.py:64-68` writes `{status:'proposal', advice, profile}` only); no live LLM/memory call exists in the deployed match path; telemetry today is a bounded in-process JSON queue with no OTEL (`agent/telemetry.py:17,29-36`); do not assume perfect tick synchrony. These are project facts, not AWS-established ones.

## 1. AgentCore Memory

**Structure.** Memory splits into **short-term** (raw per-session events via `CreateEvent`/`ListEvents`/`GetEvent`, organized by `actorId`+`sessionId`) and **long-term** (asynchronously extracted, consolidated, cross-session records) [memory.html; memory-types.html]. Long-term generation is explicitly "an asynchronous process that runs in the background" performing Extraction then Consolidation [long-term-memory-long-term.html]. Nowhere is Memory described as model-weight learning — it is retained conversation-derived data only.

**Coordination fit.** The docs describe events as immutable/timestamped but state **no consistency model** (strong vs. eventual) for cross-actor reads, and give **no atomic/broadcast/barrier primitive**. Do not assert strong or weak consistency — the docs are silent. Memory therefore cannot replace the project's existing authoritative per-tick snapshot distribution; at best it is a **side-channel historical record**, not live tick-consistency fabric.

**Boundaries.** Organization uses **Actor** (end user/agent), **Session** (one conversation), and for long-term memory a **Namespace** — a `/`-delimited hierarchical path, optionally parameterized with `{actorId}`/`{strategyId}`/`{sessionId}`, from most granular to global (`/`) [memory-organization.html; memory-terminology.html]. **Important distinction: namespace path structure is an organizational/retrieval-filtering convention, not an authorization mechanism.** The docs describe namespaces as a way to keep extracted memories "organized and prevent conflicts... in multi-tenant applications" for retrieval purposes [memory-organization.html] — naming a path `/actors/alice/` does not itself stop another caller from reading it. Access control is a **separate layer**, implemented at the IAM action/resource level: the resource-based-policy examples reviewed (`PutResourcePolicy`) grant or deny specific API actions (e.g. `BatchCreateMemoryRecords`, `RetrieveMemoryRecords`) against the whole memory resource or a specific principal/role — no namespace- or actor-scoped IAM condition key was found in the pages reviewed [memory-cross-account-access.html]. For per-end-user isolation enforced at the infrastructure layer "without distributing AWS credentials to end users," AWS documents fronting Memory with an **AgentCore Gateway + OAuth + fine-grained access control (FGAC)** [memory-advanced.html] — this, not namespace naming, is the documented mechanism for actor-level isolation. **Cross-account access** is supported via resource-based policies on specific actions (`CreateEvent`, `RetrieveMemoryRecords`, batch record ops, etc.) and cross-account delivery to S3/SNS/Kinesis [memory-cross-account-access.html] — relevant directly to opponent-data leakage scope, which is an IAM-policy (and, for per-actor isolation, a Gateway/FGAC) design question, not something namespace naming alone prevents.

**Provenance/TTL/privacy.** No documented provenance/confidence/version fields exist beyond record IDs and free-form event metadata, and that metadata is **not CMK-encrypted** even though event content is [memory-types.html, "Event metadata"]. Long-term TTL (`recordExpiryDurationDays`, **minimum 31 days**) is optional and groups must share values within strategy families (semantic+user-preference vs summary+episodic); setting/removing TTL requires a **separate IAM permission** (`UpdateMemoryRecordExpirySpecification`) independent of base write/delete [long-term-record-ttl.html]. Deletion after TTL expiry is **not instantaneous** — "can typically take a few days"; expired records may still be returned by reads in that window [long-term-record-ttl.html]. Data is always encrypted at rest with AWS-owned or customer-managed KMS keys [best-practices.html]. AWS explicitly assigns **customers** responsibility for input validation against **memory poisoning and prompt injection** during `CreateEvent`/extraction — directly relevant to ingesting untrusted match-report text [best-practices.html, "Memory poisoning..."].

**Best fit.** Only a documented-consistent use: **post-match, off-tick opponent scouting / team lessons**, written once per match into a namespace keyed by opponent/match identity, read by the offline advisor before the next match. AWS gives no concept of "match" or "opponent" — that convention is yours.

**Cost/amplification.** Pricing (quoted, not invented): short-term memory ingestion/retrieval is billed "per GB of event data... Each event is billed at a minimum of 12 KB and a maximum of 64 KB, regardless of its actual size" [aws.amazon.com/bedrock/agentcore/pricing/, "AgentCore Memory"] — i.e. AWS's own stated per-event floor/ceiling, not an inference on our part; long-term memory bills per stored record (hourly) plus per retrieval call; custom extraction strategies add your own inference cost (same source). If memory is used only off-tick (one scouting write/read per match), traffic is `O(matches × players)`, not per-tick. The brief's illustrative "5f player decisions/sec → 10f requests/sec" formula is a **live per-tick usage pattern this research does not endorse**: no tick-rate `f` is established for the project, and Section 1's lack of a documented consistency/latency guarantee is itself a reason not to put Memory on the hot path — reinforced by the quoted 12 KB floor making even tiny snapshot deltas cost a full event-billing unit.

**Gaps:** no published latency figures for Memory APIs; no stated consistency model for cross-actor short-term reads; account-level entitlement/preview access is unverified.

## 2. Bedrock Foundation Models (advisor / coach use)

**APIs.** Converse/ConverseStream is the model-agnostic chat API (`bedrock:InvokeModel`/`InvokeModelWithResponseStream` permission), supports `toolConfig` and `guardrailConfig`, and Bedrock does not persist prompt content [conversation-inference.html]. **Structured outputs** enforce JSON-schema-conformant responses via `outputConfig.textFormat` (Converse) or `strict: true` tool definitions [structured-output.html]. The supported JSON-Schema subset **excludes numeric bounds (`minimum`/`maximum`/`multipleOf`), string-length constraints, recursive schemas, and external `$ref`**, and requires `additionalProperties: false` — meaning schema validation alone cannot enforce "probability in [0,1]" or similar; **application-level bound-checking remains mandatory**, matching the project's existing pattern (`agent/advisor/core.py:76-80`). First-time schema compilation "may take up to a few minutes" then is cached 24h — a latency outlier to design around even off the hot path [structured-output.html, "Request workflow"]. Schema conformance is explicitly **not** a correctness guarantee — "support... doesn't guarantee a cache hit" and nothing claims content accuracy; this is the documented line between schema validation and football-domain correctness.

**Tool use** has three modes: client-side (your code executes the tool), server-side (Bedrock invokes a registered Lambda/Gateway tool, "currently available on the Responses API"), and Anthropic-specific tool types [tool-use.html]. For a bounded advisor producing a proposal JSON for human review, **client-side tool use + `strict` schema + your own post-hoc validation** is the mode that matches the current design (no autonomous server-side execution against players); this is a design-fit observation, not a claim that other modes are unsupported or unusable for this use case in principle.

**Prompt caching vs Memory.** Prompt caching works on **repeated, eligible prompt prefixes reused across separate requests** — not confined to a single conversational "session" in the Memory sense — with "long and repeated contexts that are frequently reused for multiple queries" as the target workload [prompt-caching.html]. The cache has a TTL that "resets with each successful cache hit" (commonly 5 minutes, up to 1 hour for some models per the model table), so a prefix stays cacheable across any number of requests as long as hits keep occurring within that rolling window — it is explicitly best-effort ("doesn't guarantee a cache hit for any request") [prompt-caching.html]. This is categorically different from Memory: caching optimizes **repeated near-term inference cost/latency for a recurring prefix**, Memory is **durable, queryable, cross-session storage** with no such minute-scale expiry by default. Neither substitutes for the other.

**Injection risk.** Feeding match reports/opponent data (untrusted text) into prompts inherits the same injection responsibility AWS assigns for Memory: Guardrails (`guardrailConfig`) filters policy categories but is not documented as an injection-specific defense for tactical-advice manipulation. Treat all report-derived prompt content as untrusted regardless of source, requiring schema + bound + football-legality validation downstream.

**Deadlines/fallback.** No Bedrock page reviewed publishes a latency SLA for Converse/InvokeModel; AWS frames latency features as best-effort only. Given the project's own cold-start measurement (up to ~4.511s), any advisor/coach call must stay off the ~1s tick path with its own timeout/circuit-breaker/fallback — exactly the project's existing isolated-advisor design, which this research supports continuing unchanged.

**Model-allowlist / entitlement caveat.** Using a model successfully from the offline advisor (a developer machine or CI context) is **not evidence that the same model is entitled, allowlisted, or invokable from the deployed player-runtime's execution role/account context** — these can be governed by different IAM policies, VPC/network egress rules, or workshop-specific allowlists. Whether the project's offline advisor usage would satisfy whatever allowlist/entitlement check applies to a deployed AgentCore Runtime player is **explicitly unknown and unverified** by this research; it must be checked against the account's actual IAM policies and any workshop-specific model allowlist before relying on it, independent of whether the advisor "works" in its current offline/manual context.

**Model selection criteria (not a specific model).** (1) Verify structured-output + tool-use support per model **and per inference profile** on the model card — AWS gives a concrete example where "structured outputs aren't supported for Claude Haiku 4.5 through the India (`in.anthropic`) inference profile," i.e. feature support varies even within one model family by region routing [structured-output.html]. (2) Verify Region (`us-east-1`) availability per model at build time. (3) Check prompt-cache TTL/minimums per model if reusing static context. (4) Confirm account access — Bedrock's own pricing page shows some models are explicitly access-gated ("Non-GA Models... access is gated and requires approval... Contact your Anthropic account team" [aws.amazon.com/bedrock/pricing/]), direct evidence that model availability is not uniform per account, supporting the project's own flagged uncertainty about workshop model-allowlist access (README:326-328).

**Gaps:** account/workshop entitlement for any specific model is unverified; no numeric end-to-end latency guarantee found for any model/API.

## 3. AgentCore Code Interpreter

Runs agent-written code "securely in sandbox environments" in an isolated containerized environment [code-interpreter-tool.html, "Overview"]. Verified language support: **Python, JavaScript, TypeScript** [code-interpreter-tool.html]. Documented limits at time of writing — inline file upload up to **100 MB**, S3/terminal up to **5 GB**; default session **15 minutes**, extendable to **8 hours**; configurable network modes and CloudTrail logging [code-interpreter-tool.html] — are quoted as-is and should be re-checked at build time since such numeric limits can change. Pricing: per-second CPU + peak memory, **1-second minimum**, **128 MB minimum memory floor**, standard EC2 network transfer rates; the pricing page states, specifically for Code Interpreter, that "if your agent consumes no CPU during I/O wait, there are no CPU charges" and separately "I/O wait and idle time is free, if no other background process is running" [aws.amazon.com/bedrock/agentcore/pricing/, "AgentCore Code Interpreter"] — note this applies to **CPU consumption**; the same source still describes memory as billed "for the peak memory consumed up to that second" throughout the session lifetime, so memory billing is not necessarily zero during an idle interval, and the 128 MB floor applies regardless. No published session-setup/tool-call latency figure was found — **measure, don't assume**.

**Fit.** The five live player runtimes already execute trusted, hand-written deterministic Python in-process with no sandbox round-trip — Code Interpreter adds nothing there; it exists specifically to isolate **untrusted/agent-generated** code, not code the team already trusts. The clearest documented fit here is **offline, optional**: if an LLM advisor or future experiment pipeline generates ad-hoc analysis code (e.g., a custom match metric), running that *generated* code in Code Interpreter rather than your own CI avoids exposing a trusted environment to arbitrary generated code. **Do not claim the existing local simulator runs unmodified inside Code Interpreter** — pre-installed package coverage of its dependencies was not verified in this pass, and no AWS evidence supports that claim.

**Local trusted analysis/CI vs hosted interpreter:** local CI gives full dependency/network control without the per-session compute billing Code Interpreter uses, appropriate for all code the team already trusts; Code Interpreter trades that control for isolation of code you do *not* trust, billed per-second per session, with an unverified cold-start cost — the two serve different trust boundaries, not different performance tiers of the same job.

**Gaps:** exact session/tool latency unpublished; pre-installed library coverage of this project's dependencies not checked.

## 4. AgentCore Evaluations

**Distinct from Bedrock Model Evaluation.** AgentCore Evaluations scores **agent trace/span behavior** (tool calls, agent responses) via LLM-as-a-judge or custom logic, built on OpenTelemetry/OpenInference instrumentation from frameworks like Strands and LangGraph [evaluations.html] — a different product from Bedrock's model-evaluation jobs for static prompt/response quality.

**Prerequisites and API distinction.** The documented CloudWatch setup workflow requires compatible instrumented spans, observability export and **CloudWatch Transaction Search**, including the on-demand tutorial's retrieval of previously ingested spans [ondemand-evaluations-prereqs.html; getting-started-on-demand.html]. However, the [Evaluate API](https://docs.aws.amazon.com/bedrock-agentcore/latest/APIReference/API_Evaluate.html) itself synchronously accepts OpenTelemetry session spans in `evaluationInput` and returns scores. Its request contract does not require a CloudWatch log-group reference. Do not turn the tutorial's CloudWatch workflow into a claim that the API enforces CloudWatch provenance. Supplying independently prepared compatible spans is a candidate integration to validate; it was not exercised in this research. Online/batch managed collection and direct on-demand scoring should be considered separately. Raw football JSON logs are not automatically compatible spans in either case.

**Framework support — confirmed, not a required migration.** Supported frameworks with a dedicated page are: Strands (built-in), LangGraph (OTel or OpenInference, Python/TS), OpenAI Agents SDK, Vercel AI SDK, LlamaIndex, Google ADK, Claude Agent SDK [supported-frameworks.html]. Critically, AWS also documents **Generic framework support**: "the service supports **any agent that emits telemetry in one of these two conventions** [OpenTelemetry GenAI semantic conventions or OpenInference]... Use generic framework support when you build with a framework that has no page in this section, **or when you write your own instrumentation for a custom agent**" [supported-frameworks-generic.md]. This directly resolves the earlier open question: **adopting LangGraph is not required** to make a plain LangChain/`ChatBedrockConverse`-based advisor evaluable. What is required is emitting spans under a `scope.name` starting with `opentelemetry.instrumentation.*` or `openinference.instrumentation.*`, with a recognized identifying attribute (`gen_ai.operation.name` = `invoke_agent`/`execute_tool`/`chat`, or `openinference.span.kind`), and putting prompt/response/tool content in the documented attributes — i.e. a **custom instrumentation/schema adapter around the existing advisor call is sufficient**, with no framework rewrite needed [supported-frameworks-generic.md, "Configuration requirements"]. One caveat the same page states explicitly: scopes for "transport and infrastructure instrumentation," including **the AWS SDK (`botocore`) instrumentation and its `bedrock-agentcore` and `bedrock-runtime` scopes, are excluded** from generic framework support — so instrumenting only the underlying `boto3`/`botocore` calls that `ChatBedrockConverse` makes is **not** sufficient on its own; the advisor needs its own agent/inference-level span emission (or, as a documented minimal fallback, the `agentcore.invocation.user_prompt`/`agentcore.invocation.agent_response` attributes the AgentCore SDK also emits, which cover only the top-level prompt/response, not inference or tool spans) [supported-frameworks-generic.md, "Supported conventions"; "Configuration requirements"].

**Evaluator types.** **Built-in** evaluators are fixed LLM-as-judge configs (e.g. `Builtin.Helpfulness`), ARN-addressable, unmodifiable [built-in-evaluators-overview.html]. Ground-truth fields (`expectedResponse`, `assertions`, `expectedTrajectory`) attach reference answers; three trajectory evaluators (`ExactOrderMatch`/`InOrderMatch`/`AnyOrderMatch`) check **tool-call sequences programmatically, with no LLM call** [ground-truth-evaluations.html] — but these check *tool calls*, not football physics. **Custom code-based evaluators** are the one mechanism matching deterministic numeric ground-truth: your own AWS Lambda receives `evaluationInput.sessionSpans` JSON and returns `{"label", "value", "explanation"}`; documented limits at time of writing are max Lambda timeout **5 minutes**, max input **6 MB** (verify current values at build time) [code-based-evaluators.html]. This is the only documented path to check formation legality/GK reachability/pass-sprint kinematics deterministically — but only for whatever numeric facts you deliberately instrument into spans; **Evaluations does not independently compute football physics or legality.**

**Evaluation types.** **Online** evaluation continuously samples (percentage/conditional) live production traffic from already-emitted, already-exported telemetry for scoring and dashboarding [evaluations-types.html]. No AWS page reviewed states an explicit non-blocking SLA, and that absence alone doesn't prove online evaluation is unsuitable near live play — the better-supported reasoning is causal: the service's own description reads it as consuming **sampled, already-recorded telemetry** rather than sitting inline on the agent's response path, so whether it blocks a tick is a property of **how you wire the integration** (e.g., fire-and-forget export, reading CloudWatch after the fact) rather than something the service forces either way. "Online evaluation should not block the tick" is therefore best treated as **a project integration discipline to enforce yourselves**, not an AWS-guaranteed property. **On-demand** evaluation scores specific, already-recorded `traceId`/`spanId`s on request — explicitly suited to "early stages of the agent development lifecycle, such as build-time testing" [on-demand-evaluations.html] — it is a **scoring step on existing telemetry, not a simulator re-run**; it does not execute your agent. **Batch** evaluation discovers sessions from a CloudWatch Logs location and scores many at once with aggregate + per-session results, for baseline/regression/periodic audits [evaluations-types.html] — same caveat: scores sessions that already happened. A separate **Simulation** feature drives LLM-backed *synthetic end-user* conversations against your agent (`pip install 'bedrock-agentcore[simulation]'`, requires `bedrock:InvokeModel` for the actor model) [simulation.html] — this is conversational-robustness testing, **not** a mechanism for running two heldout deterministic team profiles against each other; do not conflate the two.

**Quotas.** Documented at time of writing: up to **1,000 evaluation configurations per Region per account**; **1M input+output tokens/minute** for large regions [evaluations.html] — treat as current-state figures to re-verify, not permanent limits.

**Can it evaluate the current deterministic agents as-is?** Not without new instrumentation work, though the work is smaller than previously framed: (1) Telemetry isn't yet OTEL/Transaction-Search exported — this gap is real regardless of framework choice. (2) The advisor does **not** need to be rewritten onto LangGraph — Generic framework support means a targeted custom-instrumentation/schema-adapter layer around the existing `ChatBedrockConverse` call (emitting the documented `gen_ai.*`/`openinference.*` attributes, not merely relying on `botocore` auto-instrumentation, which is explicitly excluded) is sufficient to make it evaluable. (3) Deterministic per-tick decisions aren't LLM/tool-call interactions at all, so built-in and trajectory evaluators have nothing native to score — a custom code-based evaluator fed by deliberately-added spans is the only route, and that is new instrumentation/Lambda work, not a free capability over existing logs. **No automatic match outcome/win-rate computation exists** anywhere in the service; any football-outcome metric must be your own custom evaluator logic.

**Realistic near-term use:** on-demand evaluation as a build-time test gate for the advisor subsystem (report-faithfulness via custom LLM judge; schema/bound compliance via a cheaper code-based evaluator), using a custom instrumentation/schema-adapter layer rather than a framework migration; batch evaluation later for regression checks across logged advisor sessions.

**Gaps:** exact span-attribute coverage achievable from `langchain_aws.ChatBedrockConverse` specifically (vs. hand-rolled instrumentation) was not tested; whether online evaluation's integration can be made genuinely non-blocking depends on implementation choices this research did not design; per-evaluation $ cost not computed (billed by tokens processed, no flat rate published) [aws.amazon.com/bedrock/agentcore/pricing/].

## 5. Recommendation matrix

| Capability | Verdict (research candidate, not an approval) | Key reason | Gate before reconsidering |
|---|---|---|---|
| Memory — live per-tick coordination | **Not recommended for our current controller** | No documented tick barrier/atomic coordination contract; additional network calls and stale-data risks | Establish a concrete history-dependent benefit, correctness under delayed messages and measured latency before reconsidering |
| Memory — post-match opponent scouting (off-tick) | **Recommended candidate, optional** | Matches documented async long-term design; namespace organizes retrieval (not access control) | Define opponent/match identity convention; add real access control via IAM/Gateway+FGAC, not namespace naming alone; sanitize input before `CreateEvent`; set TTL ≥31 days |
| Bedrock — between-match scouting & bounded advisor JSON | **Recommended candidate, as already designed** | Structured outputs give schema conformance, not correctness — matches existing Pydantic bound-check gate | Verify model+Region+feature availability and account allowlist before any specific model choice; offline advisor access does not confirm deployed-player-runtime entitlement |
| Bedrock — narrow live in-match coach preset | **Defer** | Adds unmeasured inference latency to a tight budget; the 4.511s measurement is Runtime transport, not model inference | Reconsider only as a non-blocking, versioned, expiring preset proposal with deterministic behavior when absent; no live formation changes |
| Prompt caching | **Recommended candidate, opportunistic** | Latency/cost win for repeated eligible prefixes across requests; best-effort, not a reliability or memory mechanism | None blocking |
| Code Interpreter — sandboxing untrusted/generated analysis code | **Recommended candidate, optional, offline** | Documented purpose is isolating untrusted code | Check pre-installed packages vs. script deps first |
| Code Interpreter — hosting the local simulator | **Reject (as scoped)** | No evidence it runs unmodified; no demonstrated benefit over local CI | Would need an explicit packaging/dependency audit |
| Evaluations — scoring current deterministic player decisions | **Reject (as instrumented today)** | No OTEL export; decisions aren't LLM/tool-call interactions | Add OTEL purely for observability (never gating ticks) + a custom code-based evaluator |
| Evaluations — scoring the offline advisor | **Recommended candidate, optional, build-time first** | On-demand evaluation explicitly fits build-time testing; Generic framework support means **no LangGraph migration required** | Add a custom instrumentation/schema-adapter layer emitting the documented `gen_ai.*`/`openinference.*` span attributes around the existing advisor call (the underlying `botocore`/`bedrock-runtime` auto-instrumentation alone is explicitly excluded and insufficient) |
| Evaluations — automatic win-rate / tactical benefit vs heldout opponents | **Reject as built-in; defer as custom build** | No football-outcome capability exists; Simulation ≠ team-vs-team replay | Only via a bespoke custom code-based evaluator fed by your own instrumented spans |
| Evaluations — online production monitoring of match path | **Defer** | No explicit non-blocking SLA found; whether it blocks is an integration-design choice, not forced either way; telemetry prerequisite gap unresolved | Close OTEL gap off the hot path and design/verify a non-blocking integration empirically |


## 6. Decision gates / research gaps (not an implementation plan)

1. Memory: confirm account entitlement in `us-east-1`; define identity/namespace convention (for organization, not access control); decide real access-control mechanism (IAM resource/action policy, or Gateway+FGAC for per-actor isolation) plus CMK + TTL before any write.
2. Models: verify per-model Region/feature/account access before naming a candidate; keep proposal→approval→test→deploy gate unchanged; separately confirm whether the deployed player-runtime's execution context has the same model entitlement the offline advisor happens to have (not established either way here).
3. Code Interpreter: validate one concrete untrusted-code use case and its dependency coverage; measure real session latency.
4. Evaluations: design and build a custom instrumentation/schema-adapter layer around the existing advisor call (Generic framework support confirms this does not require migrating to LangGraph); add OTEL off the hot path only; decide if a custom code-based evaluator for football-specific legality/kinematics is worth building — nothing built-in provides it.
5. None of the above justifies adding latency risk, shared state, or network/model dependency to the five seats' live per-tick decision path; all are additive, offline/off-tick tooling around the existing deterministic controller.
6. These are research findings only; adopting any item above into the project's actual architecture is a separate decision for the team, not something this research authorizes.

- Account/workshop entitlement or allowlist status for any Bedrock model, Memory, Code Interpreter, or Evaluations feature — and specifically, whether the offline advisor's own model access would satisfy a deployed-player-runtime allowlist/entitlement check, which is a distinct, unconfirmed question.
- Numeric latency for Memory APIs or Code Interpreter session/tool-call round trips — unpublished.
- Consistency model (strong/eventual) for Memory short-term reads across actors — docs silent.
- Whether a `langchain_aws.ChatBedrockConverse`-based advisor, once given custom instrumentation per Generic framework support, actually produces well-formed, fully-attributed spans in practice — the documented *mechanism* exists, but it was not exercised/tested here.
- Whether Evaluations' online monitoring can be made genuinely non-blocking in a specific integration — depends on implementation choices not designed in this research.
- Whether directly supplied, independently prepared spans work with our chosen on-demand evaluator/account; the Evaluate API accepts spans inline, but this research made no service calls.
- Exact $ cost per evaluated session, Memory call, or advisor call — billing dimensions are documented, flat rates are not; no estimate computed here.
